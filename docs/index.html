Module 2.10 — Distributed Stream Processing

From "process yesterday's data today" to "process data as it arrives." A beginner-friendly walkthrough of Apache Kafka and Spark Structured Streaming — no prior streaming experience needed.

🍕 The scenario: FreshCart's delivery team needs the customer to see a live tracking update within seconds of a rider picking up an order — not after tomorrow's batch job. The fraud team needs to flag a suspicious transaction as it happens. This is why we need to move from batch to stream.
Where we are

Why leave batch behind?

Everything you've learned so far — SQL, DataFrames, the data warehouse — assumed data sits still while you query it. Batch processing runs on a schedule: collect a day's data, then process it. That's perfect for a monthly sales report. It's useless for a live delivery map.

🗄️

Batch processing

Process yesterday's data today. Runs on a schedule (hourly, nightly). High latency, high throughput. Good for reports, training data, historical analysis.

⚡

Stream processing

Process data the instant it arrives, one event (or micro-batch) at a time. Low latency. Good for live tracking, fraud alerts, real-time dashboards.

Connecting the dots This isn't a replacement for batch — it's a second tool. Lambda architecture (from an earlier lesson on data architectures) runs both paths in parallel: a fast streaming path for "good enough right now," and a slow batch path for "fully correct eventually." Knowing when to reach for which is what separates a senior data engineer from a junior one.
Part 1 — Event Streaming

Meet Apache Kafka

Kafka is the backbone most real-time systems are built on. Think of it as a durable, ordered notice board that many people can post to and many people can read from — independently, at their own pace.

📥 Consumer reads events
📨

Producer

An app that publishes events to a topic. In our lesson: a script generating fake pizza orders.

🏷️

Topic

A named log of events — e.g. pizza-orders. Producers write to it; consumers read from it.

🔢

Offset

A bookmark — the position of a message in the log. Consumers track their own offset, so they never lose their place.

📥

Consumer

An app that subscribes to a topic and reads events, starting from earliest or latest offset.

🧩

Partition

A topic is split into partitions so it can scale across machines. Our demo topic uses just one.

🖥️

Broker

The Kafka server that stores the log and serves producers/consumers. We run one locally via Docker.

Why this matters for FreshCart Every order, delivery update, and payment event gets published once to Kafka. The tracking team, the fraud team, and the analytics team can each run their own consumer over the same durable log — independently, without waiting on each other.

This mirrors notebook/5m_data_2_10_01_Fake_Data_Kafka_Producer.ipynb and ..._02_Hands_on_with_Kafka.ipynb. Click below to see how offsets work — notice the consumer only ever moves forward, one message at a time, and two consumers can read the same topic at completely different positions.

Consumer A (auto_offset_reset=earliest)
next offset to read: 0

next offset to read: 0

Notice: producing doesn't push data to consumers. Messages just sit in the log at their offset until a consumer polls for them — even if that's much later. This is what makes Kafka durable and lets multiple independent readers exist.

consumer = KafkaConsumer(
    bootstrap_servers=['localhost:9092'],
    auto_offset_reset='earliest',
    value_deserializer=lambda v: json.loads(v.decode('ascii')),
)
consumer.subscribe(topics=["pizza-orders"])

for message in consumer:
    print(message.partition, message.offset, message.value)
Part 3 — Hands-on with Spark

Spark Structured Streaming

Here's the one idea that unlocks everything: a stream is just a table that never stops growing. Every new event is a new row appended to an "unbounded" input table. Spark re-runs your query on the new rows every trigger interval — the same DataFrame API you already used on static data.

→
Result table (revenue by shop)

Reading a topic in batch mode

pizza_df = spark.read \
  .format("kafka") \
  .options(**options) \
  .load()

Reading the same topic as a stream

pizza_df = spark.readStream \
  .format("kafka") \
  .options(**options) \
  .load()

query = parsed_df.writeStream \
  .format("console") \
  .start()
Key concept Only read → readStream and write → writeStream changed. Every DataFrame transformation you already know — select, groupBy, from_json — works unmodified on the stream. Your batch skills transfer directly.

The data engineering lifecycle has both paths. Lambda architecture runs them in parallel, fed by the same Kafka topics. Choosing — and eventually unifying — batch and stream pipelines is core architectural judgment for a data engineer.
